# 💬 astrbot_plugin_context_compressor (无感压缩上下文)

这是一个我自己写给自己用的 AstrBot 会话上下文管理插件。核心目的就是为了复刻官方的上下文压缩归档功能，但去掉了官方方案中各种不爽的脆性限制，用更优雅、更符合直觉的异步方式来管理长文本对话。

## 🛠️ 它跟官方/传统方案有什么区别？

### 1. 拒绝简单粗暴的“夹断（Truncation）”

官方或一些传统的截断机制，在上下文爆舱时会直接把最早的聊天记录无情扔掉，导致 AI 秒变健忘症。本插件**不管怎么裁剪历史，都会先把要删掉的老历史打包提炼成一份精炼的“前情提要”**，然后把这份长期记忆作为背景知识注入到新一轮的 Context 中，确保核心线索永远不丢。

### 2. 更符合人类直觉的触发条件

和官方单一或固定的判断水线不同，本插件提供双重阀门判定，满足任意一个（`OR` 关系）就会自动在后台干活：

* **达到设定的对话轮数**：严格按照一问一答算 1 轮，绝不拿单条消息数滥竽充数。
* **达到设定的最大 Context Token 数量**：字数堆积过多、快要爆舱时自动拦截。

### 3. 全民手动清洗

觉得 AI 开始胡言乱语或者当前堆积的文本太臃肿？不用等系统自动触发，任何人在对话框发送指令 `/compress` 即可立刻对当前窗口执行一次手动的同步历史瘦身。

---

## 🚀 核心黑魔法：双管齐下的异步后台处理

这是本插件最核心的性能优化点。如果是传统的同步压缩方案，一旦触发总结，用户当前发的消息就得原地傻等几秒钟，直到大模型把长文本总结完了才会给出回复，体验极差。

本插件采用了**后台异步状态机轮询**的机制，在不写复杂硬锁的前提下，达成了类似“双线程”并发的处理效果：

1. **当前对话全速放行**：当新到来的用户消息 A 达到了你设定的压缩阈值时，插件在消息入口**绝不拦截**，直接放行。主对话大模型拿着完整的全文 Context + 消息 A 去正常请求响应。由于历史没有被动过，**100% 完美命中前缀缓存（Prefix Caching）**，AI 依然能以极速响应用户。
2. **背景任务并发提炼**：与此同时，插件在后台直接开辟一个独立的异步协程任务。它会秒级轮询 SQLite 状态，一边静默等待当前这轮回复安全落库，一边**并发发起另一个大模型总结请求**（全文 Context + 压缩指令）。由于使用的是相同的长历史前缀，这个总结请求同样能 **100% 享受到前缀缓存的超低资费和极速响应**。
3. **静默洗牌服务下轮**：总结任务在后台拿到“前情提要”后，会对数据库执行无损切片和历史重组。这个压缩后的崭新上下文会**静静地躺在数据库里，等待你的下一条消息 B 注入时才会正式生效**。

整个过程对当前的请求没有任何影响，用户完全感受不到长文本总结带来的数秒卡顿，彻底打破了线性等待的焦虑。

## ⚙️ 自由度极高的物理环境组合配置

再也不用全局一刀切了。插件面板支持你针对不同的运行环境，自由组合定制具体的压缩参数和控制水线：

* **大模型与平台机器人交叉锁定**：你可以专门为某款大模型设置一套比较宽松的 Token 触发线；或者专门为 QQ 官方机器人（例如 `qq_bot_01`）的群聊场景设置一个更严格的物理轮数水线，防刷防爆。
* **总结模型独立指派**：在专属规则卡片里，你可以强制指定某一个便宜好用或长文本能力强的模型专门负责干后台总结历史的苦力活。如果不填，它也会非常聪明地直接继承并调用当前窗口正在聊天的对话模型，把折腾降到最低。
